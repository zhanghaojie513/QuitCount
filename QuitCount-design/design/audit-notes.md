## A 类 · 结构性问题（影响多屏，优先修）

### A0 ★ Tab 栏没落底（已修）——「内容一短，Tab 栏就浮在半空」
- **现象**：s22 忍住 / s23 取出成功 等屏，内容结束后 Tab 栏就**紧贴在内容下方**，屏幕底部留下大片空白。s22 实测 tabBottom=456（应 852）
- **根因**：18 屏的 `${TABBAR()}` 被写在 `<div class="body">` **内部**（`.body` 的最后一个子元素）。`.body{flex:1}` 确实撑到了 790px，但它的子元素没有 `flex:1`，所以 Tab 栏只是「跟着内容往下流」，而不是被压到底部
- **修法**：把闭合 `.body` 的 `</div>` 移到 `${TABBAR()}` **之前**，使 Tab 栏成为 `.screen` 的直接子元素（与 `.body` 平级）。18 屏一次性重排
- **复测**：18 个带 Tab 的屏全部 `tabBottom=852`，`body=695`（= 852 − 62 状态栏 − 95 Tab 栏），无一溢出
- **教训**：`.body{flex:1}` 只保证「body 撑满」，不保证「body 的子元素被压到底」。把固定栏放在 flex 容器**内部**时，必须显式给内容区 `flex:1`，否则就会随内容浮动

## B 类 · 单屏问题

### B0 ★ Tab 栏顺序错误（已修）——「取出」必须是正中第 3 项
- **现象**：原顺序 `首页 · 取出 · 资产 · 账本 · 我的`，「取出」被放在第 2 位
- **设计**：`首页 · 资产 · 取出 · 账本 · 我的`，「取出」是**正中间第 3 项**
- **理由**：取出不是导航 Tab，而是全栏唯一的**功能性动作位**。放正中是为了拇指可达性，也是它视觉上「跳出导航序列」的原因 —— 它是透明的、只有一个绿色图标，没有激活态
- **修法**：`TABBAR()` 重排；`app.js` 的 `TABS` 同步；移除各屏多余的单条「取出」补丁（原 `PATCH` 里 s15 的 `取出 → s02` 与其他屏冲突）
- **复测**：28 屏 × 5 Tab 全部路由正确（首页→s02 / 资产→s04 / 取出→s08 / 账本→s05 / 我的→s06）；激活项不自我跳转
- **几何实测**（设计稿 2× 切片换算）：白色胶囊容器左右内缩 **22px** / 高 **59px**；激活胶囊 **66 × 54**
- **教训**：`design-full.html` 第 346 行早就写明「Tab Bar 95（中间「取出」）」，但我只读了第 197 行的尺寸行。**改构件前先把该构件的所有提及处 grep 一遍**

## D 类 · 交互死链（本轮发现并修）

**方法**：用 `phone.dataset.screen` 做探针，遍历每一屏的弹层关闭 × 与主按钮，点击后读当前屏 ID。

| 位置 | 问题 | 修法 |
|---|---|---|
| **s08 取出弹层的 ×** | `<span class="x">` **完全没有 onclick** —— 弹出后无法关闭 | 补 `onclick="goTo('s02')"` |
| **s14 的「确认清空」** | 破坏性主操作**没有 onclick** —— 点了没反应 | 补 `onclick="goTo('s15')"`（清空后即无库存 → 首页空状态） |
| **s04 的「清空库存」** | 依赖 `app.js` 的文案匹配 PATCH，隐式 | 补显式 `onclick="goTo('s14')"`，不再依赖文案 |

**同时排查通过**：全部 9 处 `class="x"` 关闭按钮现均有处理器；6 处无 `onclick` 的按钮均由 `PATCH` 的文案匹配覆盖。

**教训**：`app.js` 的「文案匹配 PATCH」是个隐式机制 —— 只要文案一改，按钮就静默失效。**关键路径的按钮应当写显式 `onclick`**，文案匹配只作为 Tab 这类批量补丁的手段。

第一版断言脚本报 **0 / 56 全红** —— 连上一轮明确通过的一起红。按既有教训**先怀疑工具**，查得：

```js
Array.from(d.querySelectorAll('*')).map(n=>n.childNodes).flat()
```

**`NodeList` 没有 `.flat()`**。`map` 返回的是 `NodeList[]`，对它调 `.flat()` 不报错但也不展开
（`.flat` 只展数组，NodeList 是类数组不是数组），于是 `.filter(n=>n.nodeType===3)` 一个都找不到 → 抽出空串 → 全红。

**固化规则**：抽取 DOM 文本时用 `Array.prototype.forEach.call(el.childNodes, …)`，不要 `map(...).flat()`。
**并且：断言批量失败时，先用手工 DOM 查一条，别急着改产品。** 这一条本轮又一次救了我。

### I10 补做空号禁用态（2026-10-03 晚 · G4 结案）

> 详见 G 类 **G4**（已标注为解决）。此处只记要点与新增的方法论。

1. **「更换号码」的落点错了**：原 `data-step="1"` → 下标 0（空号态）。但用户是**填了号**才走到步骤 ② 的，
   退回空号等于清掉刚填的号码。改为 `data-step="2"` → 已填态。
2. **`data-step` 语义本身有歧义**：它此前时而表示「1 基步骤号」、时而表示「状态组序号」。

   现统一为「直接指状态下标（1 基）」。

**第 2 条值得单独记一笔**：这是一个**被状态数增长暴露出来的隐性缺陷**。
四态时两种解释的差值是 1，恰好被"步骤①有0/1两态"掩盖；五态时差值变成 2，就露出来了。
**教训：枚举型属性（step/index/variant）在状态数变化时必须重新核对语义，不能假设它一直是对的。**

**顺带改良的全局样式**：`.btn:disabled` 原来 `border:0` + `#EFEDE8` 底，在米色页上几乎隐形。
用户会读成「这里没有按钮」而不是「按钮暂不可用」。现补 `1px solid var(--line)` 描边 + 底 `#FBFAF7`。
**注意**：`.btn` 基础是 `border:0`，所以旧规则里写的 `border-color` **根本不会渲染** ——
这是个静默失效的样式（不报错、只是没效果），排查时容易漏。

按钮（`s22`）而非 `s23`，报出假失败 —— 这是第 6 次。

```js
};
let PICKED = 'yunyan';
function afterTake(cigId){ /* → {cig,n,T,harm,burden,net,cost,dHarm,dTar,dPrice,dHealth} */ }
```

`HOME_AFTER` / `HOME_HOLD` 由 `const` 改为 `let` + `homeAfter()` / `homeHold()` 函数产出 ——
**它们是"当前选中那支烟的函数"，不再是常量。**

### K5 新增机制：[data-pick] 与 window.setPick

`08` 的两行烟现在带 `data-pick="<cigId>"`，`app.js` 的 `bindNav` 第 ⑤ 段接管：

```js
phone.querySelectorAll('[data-pick]').forEach(node=>{ /* 切选中 → 重算 → 重画，不压返回栈 */ });
```

选中项存在 `screens.js` 的 `PICKED` 里，而它**不在 `app.js` 的作用域内** ——
`screens.js` 此前什么也没挂到 `window` 上。故新增 `window.setPick(id)` / `window.getPick()`，
与既有的 `window.goTo` 是同一套「screens.js 向 app.js 暴露入口」的先例。

### K6 踩到的三个坑（都是自己写出来的）

1. **`html` 是注册时的字符串快照。** `screens.js` 里 `screen({html:…})` / `variants(id,[…])`
   都在调用那一刻把值取走。所以改 `PICKED` 后**光重渲染 app.js 不够** ——
   `22 / 23 / 02 态②` 的快照本身还是旧的。故新增 `refreshDerived()` 显式重算并写回。
   **代价**：今后每加一处依赖选中烟的展示，都要在这里登记。
2. **`bodyOf()` 在有变体时只取变体。** `08` 加了「选中 云烟细支 / 选中 中南海低焦」两个变体后，
   点烟若只改 `PICKED` 不切 `curVar`，重画会被旧变体盖掉。
   故 `[data-pick]` 处理器与**底部状态条**（`variants` 的 `pick` 字段反查）都必须同步下标。
3. **深链直达会绕过选中。** `#s08` 进屏走 `entryVarFor('s08')` → 返回 0 → 取变体[0]（云烟）。
   修复：`entryVarFor` 先判 `vs.some(v=>v.pick)`，有则**按当前 `PICKED` 定位下标**。
   这是截图验证时发现的 —— 数据全对但截图显示云烟，属于"不查就发不现"的一类。

### K7 顺带修掉：库存口径的两级混淆

`08` 弹层标「库存 12 支」，首页 / `23` 标「库存 16/17 支」—— 用户会读成同一件事，实际不是：

| 位置 | 含义 |
|---|---|
| `08` 弹层 | **单品牌**库存（云烟 12 支 / 中南海 5 支） |
| 首页 · `23` | **全部合计**库存（17 → 16 支） |

**用户拍板：加限定词区分。** 弹层改为「**本品牌**库存 N 支」，合计侧不动 ——
因为合计是首页的主指标，加限定词反而更啰嗦。

### K9 方法论沉淀（本轮新增两条）

1. **同一句抱怨复发时，要假设"上次修的是另一层"，重查而不是复用结论。**

   `verify-pick-linkage.js` 在 Node 里跑，数据链 43/43 全绿 —— 但它**看不见 `app.js` 的事件绑定**。
